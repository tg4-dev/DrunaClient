# 8. Интеграция с API

Используй `docs/FRONTEND_API.md` как основной контракт.

API возвращает envelope:

```json
{
  "data": {},
  "error": null
}
```

или:

```json
{
  "data": null,
  "error": {
    "message": "Сообщение",
    "code": 400
  }
}
```

Реализуй централизованный типизированный API-клиент, который:

- использует настраиваемый base URL;
- добавляет `Content-Type: application/json`;
- добавляет `Authorization: Bearer <accessToken>` для защищённых маршрутов;
- при необходимости создаёт `X-Request-ID`;
- корректно разбирает response envelope;
- преобразует серверные ошибки в единый тип ошибки приложения;
- обрабатывает timeout;
- обрабатывает отсутствие сети;
- не логирует пароли и токены;
- не показывает пользователю технические stack traces;
- поддерживает отмену запросов, где это необходимо.

Не распределяй логику авторизации по отдельным экранам.

# 9. Авторизация и токены

Реализуй:

- регистрацию;
- вход;
- выход;
- восстановление сессии;
- обновление токенов;
- очистку недействительной сессии.

После регистрации выполни вход, если это соответствует пользовательскому сценарию.

Храни `accessToken` и `refreshToken` только в безопасном хранилище:

- iOS Keychain;
- Android Keystore;
- либо библиотеке, использующей эти механизмы.

Не храни токены:

- в AsyncStorage;
- в обычных файлах;
- в исходном коде;
- в логах;
- в незашифрованном глобальном состоянии, если этого можно избежать.

При получении `401`:

1. Убедись, что запрос использовал access token.
2. Запусти обновление токенов.
3. Не допускай параллельного запуска нескольких refresh-запросов.
4. Остальные запросы, получившие `401`, должны дождаться одного общего обновления.
5. Сохрани новую пару access/refresh token.
6. Старый refresh token больше не используй.
7. Повтори первоначальный запрос один раз.
8. Не создавай бесконечный цикл повторов.
9. Если refresh не удался — очисти токены и переведи пользователя на экран входа.

При ручном выходе очисти токены, локальное пользовательское состояние и кэш приватных данных.

Изучи раздел push-уведомлений в API-документации и требования Figma.

Если push входит в текущую версию:

- запроси разрешение в подходящий момент, а не сразу при первом запуске без объяснения;
- корректно обработай отказ;
- получи push token устройства;
- зарегистрируй его на backend, если endpoint доступен;
- обновляй token при его изменении;
- обработай уведомление в foreground;
- обработай переход по уведомлению;
- не ломай приложение, если push недоступен в симуляторе;
- добавь необходимые инструкции по настройке APNs/FCM;
- не добавляй реальные ключи и сертификаты в репозиторий.

Если backend или Figma не позволяют закончить интеграцию, подготовь инфраструктуру и точно опиши недостающие данные.

# 25. Безопасность

Запрещено:

- добавлять production-секреты в репозиторий;
- хранить токены в обычном локальном хранилище;
- логировать пароль или JWT;
- отключать проверку HTTPS в production;
- принимать refresh token как access token;
- бесконечно повторять запросы;
- использовать реальные пользовательские данные в тестах;
- обходить ограничения backend;
- скрывать ошибки небезопасными заглушками.

Проверь, что приватные данные одного пользователя не остаются в кэше после выхода и входа другого пользователя.
