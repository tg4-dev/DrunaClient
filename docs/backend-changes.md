# Изменения, которые нужны бэкенду

Журнал для нового UI. Сюда дописывается пункт, когда клиент упирается в отсутствие endpoint или в расхождение DTO с тем, что уже вызывает приложение. Контракт, который клиент использует сейчас, описан в [`docs/legacy/server.md`](legacy/server.md) и [`context/FRONTEND_API.md`](../context/FRONTEND_API.md).

Статусы: `нужно`, `уточнить`, `есть в API`.

Сверено с сервером 2026-10-30: локальная копия DrunaServer, коммит `da44c73` от 2026-07-13. Роуты в `pkg/handler/handler.go` совпадают с `FRONTEND_API.md`, других нет. Все защищённые роуты доступны и по `/api/v1`, и по `/api` — второй путь в документации не упомянут.

## Покрытие API клиентом

«Живой UI» — то, до чего доходит приложение из `main.dart`: вход, `HomePager` (календарь, «Друзья», профиль и настройки).

Старые экраны прототипа (`lib/features/home|groups|events|profile|notifications`) всё ещё в git. Ни один экран, до которого можно дойти из `main.dart`, их не импортирует. Методы, которые вызываются только из них, помечены «только старые экраны».

Календарь пока работает на демо-событиях в памяти: ни один endpoint событий не вызывается.

| # | Endpoint | Метод `DrunaRepository` | Живой UI |
|---|---|---|---|
| 1 | `GET /ping/` | `ping` | настройки, «Проверить соединение» |
| 2 | `POST /auth/sign-up` | `signUp` | регистрация |
| 3 | `POST /auth/sign-in` | `signIn` | вход |
| 4 | `POST /auth/renew-token` | внутри `ApiClient` | автоматически на 401; проверка в настройках |
| 5 | `POST /auth/telegram` | **нет** | — |
| 6 | `GET /users/me` | `getProfile` | профиль; `telegramID` не читается |
| 7 | `PATCH /users/me` | `updateProfile` | профиль, правка имени (с 2026-10-30) |
| 8 | `GET /events/` | `listEvents()` | только старые экраны; без `limit/offset/dateFrom/dateTo`, `total` не читается |
| 9–11 | `POST /events/`, `PATCH /events/:id`, `DELETE /events/:id` | `createEvent`, `updateEvent`, `deleteEvent` | только старые экраны |
| 12 | `POST /events/free-time` | `freeTime` | только старые экраны |
| 13 | `GET /friends/list` | `listFriends` | «Друзья», friend bar |
| 14 | `GET /friends/search` | `searchFriends` | «Друзья» |

| 16–17 | `GET /friends/requests/incoming`, `…/outgoing` | `incomingRequests`, `outgoingRequests` | «Друзья»; список лежит под ключом `friends`, клиент читает его как запасной |

## Приглашения на события

- Статус: `нужно`
- **Что нужно клиенту.** Режим друзей в календаре. Удержание дня или рисование в дне при выбранных в friend bar друзьях создаёт приглашение.
  - Организатор задаёт название, дату и время (или «весь день») и описание. После подтверждения друзья должны получить приглашение.
  - Форма события показывает, кто идёт, кого ждём и кто отказался. Приглашённый отвечает «Да» или «Нет», может передумать или снять ответ (снова «ждём»). «Возможно» убрано (2026-11-01). Организатор всегда идёт, его ответ не меняется; он правит время, название и описание или отменяет событие.
  - В профиле — список всех приглашений: ждут ответа, предстоящие, прошедшие.
  - Сейчас всё это работает только на демо-данных (`DemoInvitesSource`). С сервером клиент честно пишет «Приглашения пока не поддерживаются сервером».
- **Почему текущих вызовов недостаточно.**
  - Групповое событие (`/groups/:id/events`) не имеет участников и ответов. В группу добавляют сразу, без согласия, только друзей владельца, и удалить участника нельзя. Отказаться можно только выходом из группы.
  - Единственный сигнал «подтвердил» — `confirmedTime` участника группы. При добавлении он ставится в `now()`, поэтому «ещё не ответил» из него не вывести.
  - Создавать группу на каждое приглашение значит плодить группы, которые некому удалить.
- **Предлагаемый контракт** (`/api/v1/invites`, всё под Bearer):
  - `POST /invites` `{ title, description?, startTime, endTime, allDay?, invitees: [username] }` → `{ invite }`. Звать можно только принятых друзей, иначе 400 с перечнем.
  - `GET /invites?status=pending|upcoming|past&limit&offset` → `{ invites: [Invite], total }`. Приглашения, где я организатор или участник.
  - `GET /invites/:id` → `Invite`. Не участнику — 404.
  - `PATCH /invites/:id` `{ title?, description?, startTime?, endTime?, allDay? }` — только организатор. Ответы участников при смене времени: сбрасывать в `pending` или нет — `уточнить`.
  - `DELETE /invites/:id` — только организатор; у участников приглашение пропадает.
  - `POST /invites/:id/respond` `{ status: "going" | "not_going" | "pending" }` — только сам приглашённый, сколько угодно раз; `pending` снимает ответ. Организатору — 400.
  - `Invite`: `{ id, title, description, startTime, endTime, allDay, organizer: FriendInfo, participants: [{ user: FriendInfo, status: "pending"|"going"|"not_going", respondedAt }] , createdAt, updatedAt }`.
  - Добавить и убрать участников после отправки — `уточнить`. В клиенте пока нет.
- **Связь с другими данными** — `уточнить`:
  - Должно ли «иду» входить в свободное время и в занятость друзей? Клиент рисует принятые приглашения в календаре как свои события, поэтому логично — да.
  - Проверять ли пересечение с личными событиями? Сейчас личные и групповые события не проверяются друг с другом.
- **Push:** тип `invite_created` для приглашённых, `invite_answered` для организатора, `invite_changed` и `invite_cancelled` для участников (см. «Push и device token»).

## Описание у события

- Статус: `нужно`
- Зачем клиенту: у приглашения есть описание («где встречаемся, что взять»). Для личных событий поле тоже пригодится.
- Что отсутствует: в DTO события только `title`, `startTime`, `endTime`, `type`.
- Предлагаемый контракт: `description: string` (до 2000 символов) в create/update/list личных и групповых событий и в `Invite`.

## Push и device token

- Статус: `нужно`
- **Зачем клиенту:** о новых приглашениях, ответах на них и заявках в друзья пользователь узнаёт, только открыв приложение. Список в профиле обновляется при загрузке.
- **Что есть на сервере:** таблица `notification_outbox` (`user_id`, `type`, `payload`, `created_at`, `delivered_at`) с типами:
  - `friend_request` `{fromUsername}`;
  - `group_confirm` `{groupId}`;
  - `group_event_created` `{groupId, eventId, title, startTime}`.
  Отправки нет, и прочитать outbox нельзя: endpoint отсутствует.
- **Что отсутствует:**
  - регистрация device token: `POST /api/v1/devices` `{ token, platform: "ios"|"android" }`;
  - снятие токена при выходе: `DELETE /api/v1/devices/:token`;
  - доставка через APNs или FCM — `уточнить`, нужен ключ APNs и аккаунт Apple Developer;
  - чтение уведомлений внутри приложения: `GET /api/v1/notifications?since=` → `{ notifications: [{ id, type, payload, createdAt, readAt }] }` и `POST /api/v1/notifications/read` `{ ids }`;
  - типы для приглашений (см. «Приглашения на события»).
- На клиенте push-инфраструктуры нет: entitlements, `firebase_messaging` и запрос разрешения отсутствуют.

## Список событий: пагинация и диапазон

- Статус: `есть в API`, клиент не использует
- Зачем клиенту: календарь листается на месяцы вперёд и назад. Когда он перейдёт на сервер, ему нужны события видимого диапазона.
- Что не так: `GET /events/` по умолчанию отдаёт 50 событий. `DrunaRepository.listEvents()` не передаёт `limit`, `offset`, `dateFrom`, `dateTo` и не читает `total`, поэтому всё после 50-го теряется.
- Что сделать на клиенте: передавать `dateFrom`/`dateTo` видимых недель. Серверу — подтвердить, что фильтр по диапазону учитывает события, начавшиеся раньше `dateFrom`, — `уточнить`.

## Свободное время: часовой пояс и групповые события

- Статус: `уточнить`
- Что не так:
  - `POST /events/free-time` и `/groups/:id/free-time` берут день из строки `date` через `time.Parse("2006-01-02")`, то есть как сутки UTC. Клиент передаёт локальную дату, и у пользователя в UTC+3 окна сдвинуты на 3 часа.
  - Личное свободное время не учитывает групповые события пользователя (`group_id IS NULL`), хотя групповое учитывает личные события каждого участника.
  - Запрос только на один день.
- Предлагаемый контракт: принимать `timezone` (IANA) или `dateFrom`/`dateTo` в RFC 3339 с поясом. Учитывать групповые события и, когда появятся, принятые приглашения. Диапазон в несколько дней — `уточнить`.

## Группы: подтверждение времени и участники

- Статус: `уточнить`
- Что не так:
  - `confirmedTime` группы ставится при создании и больше не меняется; `POST /groups/:id/confirm` пишет только время участника.
  - `GET /groups/:id` отдаёт `confirmedTime` каждого участника, но модель клиента `GroupSummary` его теряет: участники читаются как `FriendInfo`.
  - В список групп (`/groups/list`) участники не входят.
  - Убрать участника нельзя, добавить можно только без его согласия.
- Зачем: новый UI групп пока не строится. Приглашения (см. выше) закрывают сценарий «позвать друзей на событие». Нужны ли постоянные группы, решит продукт.

## Друзья: поиск и аватары

- Статус: `нужно`
- Что не так:
  - `GET /friends/search` ищет по префиксу ника и возвращает самого пользователя и уже добавленных друзей. Клиенту приходится фильтровать их сам.
  - В `FriendInfo` нет ни `avatarURL`, ни цвета, поэтому аватары друзей — только буква и цвет по id.
- Предлагаемый контракт: исключать себя из поиска. Добавить статус связи `friend|incoming|outgoing|none` к каждому результату. `avatarURL` и `color` (см. «Цвет профиля») — в `FriendInfo`.

- Статус: `уточнить`
- Зачем клиенту: в профиле по образцу Locket планировались «Скопировать ссылку» и «Поделиться». Сейчас их нет: ссылки на профиль у сервера нет.

- Предлагаемый контракт: не фиксировать до решения о домене и deep link.

## Опросы и гостевые приглашения

- Статус: `нужно`
- Зачем клиенту: welcome предлагает «Ответить на приглашение без аккаунта». Сейчас это сообщение о недоступности, запроса нет.
- Что отсутствует: создание опроса, гостевая ссылка, ответ без сессии, список ответов для организатора.
- Предлагаемый контракт: не фиксировать, пока нет экранов нового UI. Гостевой ответ на приглашение логично строить поверх «Приглашений на события» — `уточнить`. Не подменять успехом локальную заглушку.

## Календари Apple, Google и Outlook

- Статус: `нужно`
- Зачем клиенту: события внешних календарей не попадают ни в свободное время, ни в занятость для друзей. В новом UI пункта для подключения пока нет: он был только в старом экране профиля.
- Что отсутствует: OAuth или системное разрешение, привязка календаря, импорт занятых интервалов в расчёт free-time.
- Предлагаемый контракт: не фиксировать до продуктового решения, чей календарь считается источником занятости.

## Профиль: имя и аватар

- Статус: `нужно`
- **Что есть:** `PATCH /users/me` принимает `name` и `avatarURL`. С 2026-10-30 профиль в новом UI правит имя.
- **Что не так:**
  - SQL обновляет поля через `COALESCE(NULLIF($x,''), …)`: пустая строка значит «не менять». Поэтому имя нельзя стереть (клиент и не даёт), а аватар нельзя убрать.
  - Загрузки файла нет: только URL уже размещённой картинки. Выбора фото с устройства в новом UI нет, люди везде показываются цветом и буквой.
  - `username` и `email` не меняются.
- **Предлагаемый контракт:**
  - upload аватара (multipart или presigned URL) с возвратом постоянного URL — `уточнить` вместе с лимитом размера;
  - `avatarURL: null` убирает аватар.

## Событие на весь день

- Статус: `нужно`
- Зачем клиенту: в листе события нового календаря есть переключатель «Весь день». Событие на весь день рисуется полосой без времени, в том числе на несколько дней подряд. Пока календарь работает на демо-данных, флаг живёт только в памяти. Приглашение тоже может быть на весь день.
- Что отсутствует: в DTO события есть только `title`, `startTime`, `endTime`, `type`. Сервер не отличает «весь день» от события 00:00–00:00, а `endTime` должен быть строго позже `startTime`.
- Почему текущих вызовов недостаточно: если хранить «весь день» как 00:00 → 00:00 следующего дня, то настоящая встреча с полуночи до полуночи станет неотличима от события на весь день. Кроме того, у UTC-времени полночь в одном поясе — это середина дня в другом.
- Предлагаемый контракт: поле `allDay: bool` в create/update/list для личных и групповых событий и в `Invite`. Для `allDay = true` даты передаются без времени (`startDate`, `endDate`, конец включительно) или как полночь в поясе владельца — нужно `уточнить`. Уточнить также, как такие события учитывает `free-time`.

## Повторяющиеся события

- Статус: `нужно`
- Зачем клиенту: в листе события есть «Повтор»: каждый день, каждую неделю (с выбором дней Пн–Вс), каждые 2 недели, каждый месяц, каждый год, «Дополнительно» (каждые N дней, недель, месяцев или лет) и окончание повтора (никогда или дата). Сейчас серия разворачивается на клиенте и не сохраняется.
- Что отсутствует: поле правила повтора в событии, развёртывание повторов в `GET …/events` по `dateFrom`/`dateTo`, учёт повторов в `free-time` и в проверке пересечений, правка и удаление одного повтора или всей серии.
- Почему текущих вызовов недостаточно: создать копии события на N недель вперёд можно, но тогда серия не связана: «изменить все» и «удалить все» невозможны, бесконечный повтор не выразить, а сервер отклонит копии, которые пересекаются с другими событиями.
- Предлагаемый контракт: поле `repeat` по мотивам RRULE (RFC 5545): `{ "freq": "daily|weekly|monthly|yearly", "interval": 1, "byWeekday": [1, 3], "until": "YYYY-MM-DD" | null }`. В списке событий — развёрнутые повторы с `seriesID` и датой повтора. Правка одного повтора — `уточнить` (исключения EXDATE или отдельное событие-исключение). У приглашений повтора нет.

## Занятость друзей

- Статус: `нужно`
- Зачем клиенту: в календаре друзей (friend bar) выбранные друзья показываются полосами занятости их цвета. Без сервера клиент рисует только демо-расписания (переключатель в настройках), а в обычном режиме честно пишет «Расписание друзей пока недоступно».
- Что отсутствует: способ получить занятость друга. `GET /api/v1/events` отдаёт только свои события, `POST /groups/:id/free-time` — только общие свободные окна группы, и то по одному дню.
- Почему текущих вызовов недостаточно: окна группы не говорят, кто именно занят и когда, требуют создать группу и не покрывают месяц.
- Предлагаемый контракт: `GET /api/v1/friends/:username/busy?dateFrom=YYYY-MM-DD&dateTo=YYYY-MM-DD` → `{ "busy": [{ "startTime", "endTime", "allDay" }] }` — интервалы без названий и типов, повторы уже развёрнуты, принятые приглашения включены. Только для принятых друзей. Нужна ли отдельная настройка приватности («скрывать занятость») — `уточнить`. Вариант для нескольких друзей одним запросом — `уточнить`.

## Цвет профиля

- Статус: `нужно`
- Зачем клиенту: пользователь выбирает свой цвет в профиле (16 цветов палитры аватаров). Им рисуются его события, аватар, его доля градиента приглашений и, по задумке, его занятость у друзей.
- Что отсутствует: поле для цвета в профиле. Сейчас выбор хранится только на устройстве, а друзья видят цвет, вычисленный по id. Поэтому градиент одного и того же приглашения у организатора и у гостей может отличаться.
- Почему текущих вызовов недостаточно: `PATCH /api/v1/users/me` принимает только `name` и `avatarURL`; в `FriendInfo` цвета нет.
- Предлагаемый контракт: `color` — индекс палитры 0–15 (или `null` — по id) в `GET/PATCH /api/v1/users/me` и в `FriendInfo` списков друзей, поиска и участников приглашения. Хранить индекс, а не hex, чтобы палитру можно было менять на клиенте — `уточнить`.

## Вход через Telegram

- Статус: `есть в API`, клиент не использует
- `POST /auth/telegram` `{ initData }` выдаёт пару токенов. Метода в `DrunaRepository` нет. Нужен ли вход через Telegram в мобильном клиенте — продуктовое решение.

## Как дописывать

Каждая новая запись:

1. Что нужно клиенту (экран или сценарий).
2. Предлагаемый endpoint или изменение DTO, если оно уже ясно. Если нет — статус `уточнить` и вопрос, без выдуманного пути.
3. Зачем это нельзя сделать текущими вызовами из `DrunaRepository`.
4. Статус.
