# Изменения, которые нужны бэкенду

Журнал для нового UI. Сюда дописывается пункт, когда клиент упирается в отсутствие endpoint или в расхождение DTO с тем, что уже вызывает приложение. Контракт, который клиент использует сейчас, описан в [`docs/legacy/server.md`](legacy/server.md) и [`context/FRONTEND_API.md`](../context/FRONTEND_API.md).

Статусы: `нужно`, `уточнить`, `есть в API`.

Сверено с сервером 2026-10-30: локальная копия DrunaServer, коммит `da44c73` от 2026-07-13. Роуты в `pkg/handler/handler.go` совпадают с `FRONTEND_API.md`, других нет. Все защищённые роуты доступны и по `/api/v1`, и по `/api` — второй путь в документации не упомянут.

## Покрытие API клиентом

«Живой UI» — то, до чего доходит приложение из `main.dart`: вход, `HomePager` (календарь, «Друзья», профиль и настройки).

Старые экраны прототипа удалены 2026-11-02. Методы, которые вызывались только из них, помечены «только старые экраны»: сейчас их не вызывает никто, они ждут нового UI.

Календарь пока работает на демо-событиях в памяти: ни один endpoint событий не вызывается.

## Цвет и шрифт аватара

- Статус: `нужно`
- **Что нужно клиенту.** Пользователь выбирает цвет аватара (один из 8) и шрифт буквы (один из 6) на шаге «Профиль» онбординга и в настройках (`docs/design-system.md` §9.11, `docs/avatar.md`). Друзья должны видеть его аватар таким же: в списке друзей, friend bar, на событиях и приглашениях.
- **Что есть.** У пользователя только `avatarURL`. Сейчас выбор хранится на устройстве (`AppSettings`): на другом телефоне и у друзей его нет, друзья получают цвет по id и шрифт по умолчанию.
- **Предлагаемый контракт.**
  - `avatarColor: int` — индекс палитры 0–7.
  - `avatarFont: string` — id шрифта: `onest`, `playfair`, `lobster`, `oswald`, `unbounded`, `comfortaa`.

  Где:
  - в `GET /users/me`;
  - в `PATCH /users/me` (оба необязательны);
  - в `FriendInfo` — списки друзей, поиск, заявки, участники.

  Неизвестный id шрифта клиент показывает шрифтом по умолчанию, индекс вне палитры — цветом по id.
- Регистрация: те же поля в `sign-up` или сразу следующим `PATCH`, чтобы выбор из онбординга не терялся — `уточнить`.

## Вход и регистрация по почте

- Статус: `не будет` (ответ бэкенда, 2026-11-04). Вместо почты — коды через Telegram, см. ниже.
- С 2026-11-04 клиент входит по нику и паролю (`sign-in`) и регистрируется через `sign-up` без подтверждения почты (`docs/design-system.md` §9.9). Экраны почты-входа и кода выключены блоком (`OnboardingController.verifyEmail`).
- **Не хватает для входа по нику.**
  - Есть ли аккаунт с таким ником — публично, до входа. Сейчас на неверный пароль клиент пишет «неверный ник или пароль» и предлагает создать аккаунт с этим ником. Предложение: `GET /auth/username/:username` → `{ "exists": true }` под rate limit `/auth/*` — `уточнить`.
  - Занятость ника до отправки регистрации — то же предложение; сейчас «ник занят» приходит только из `sign-up`.

## Вход и регистрация через Telegram

- Статус: `уточнить` — механизм у бэкенда ещё не выбран.
- **Решено.** Пароль остаётся (решение автора, 2026-11-04): при регистрации его придумывают, входят по нику и паролю. Telegram заменяет подтверждение почты. Новые шаги онбординга — по дизайну автора, отдельным заходом.
- **Почему текущих вызовов недостаточно.**
  - `POST /auth/telegram` принимает `initData`. Его подписывает только клиент Telegram внутри Mini App, нативное приложение его получить не может.
  - `sign-up` на занятые почту или ник отвечает HTTP 500 с текстом Postgres (`pq: duplicate key value violates unique constraint …`). Клиент угадывает поле по тексту (`takenOr`). Нужно: 409 и поле, например `{ "error": { "code": 409, "field": "username", "message": "…" } }`.
  - Свободен ли ник, можно узнать только из защищённого `/friends/search`, до регистрации он недоступен.
- **Варианты для обсуждения с бэкендом** (все публичные `/auth/*`, под общим rate limit, одноразовые короткоживущие коды и токены):
  1. **Код от бота.** Приложение открывает `t.me/<bot>`, бот присылает 6-значный код.
     - `POST /auth/telegram/code/start` → `{ requestId, botUrl, expiresIn }`;
     - пользователь нажимает Start в боте, бот присылает код;
     - `POST /auth/telegram/code/verify` `{ requestId, code }` → `{ signupToken }` для нового аккаунта или пара токенов для существующего.
     - На клиенте остаются ячейки кода (`CodeBoxes`). Автозаполнения кода из Telegram у iOS нет — только ввод или вставка.
  2. **Подтверждение кнопкой в боте, без кода.**
     - `POST /auth/telegram/link/start` → `{ nonce, botUrl: "t.me/<bot>?start=<nonce>", expiresIn }`;
     - пользователь нажимает в боте «Подтвердить»;
     - клиент опрашивает `GET /auth/telegram/link/<nonce>` → `pending` | `{ signupToken }` | пара токенов.
     - Ввода нет совсем, но нужен возврат из Telegram в приложение (опрос при возвращении на экран).
  3. **Telegram Gateway по номеру телефона.**
     - `POST /auth/phone/start` `{ phone }` → `{ requestId, resendAfter }`; Telegram сам присылает код в чат «Verification Codes»;
     - `POST /auth/phone/verify` `{ requestId, code }` → как в варианте 1.
     - Gateway платный, за каждый код; в приложении появляется шаг ввода номера.
- **Нужно в любом варианте.**
  - `POST /auth/sign-up` `{ signupToken, name, username, password }` → сразу пара токенов; Telegram-аккаунт берётся из токена.
  - `GET /auth/username-available?username=` → `{ available: bool }`. Правила ника как в клиенте: 3–32 символа `a–z 0–9 _ .`, без учёта регистра; неверный формат — 400.
  - `POST /auth/sign-in` `{ username, password }` — как сейчас; неверная пара — 401, клиент показывает «неверный пароль» по коду, а не по тексту.
- **Apple и Google.** Кнопки на welcome — плейсхолдеры. Понадобятся:
  - `POST /auth/apple` `{ identityToken, name? }`;
  - `POST /auth/google` `{ idToken }`.

  Оба → пара токенов. Новый пользователь после них проходит шаги ника и имени — `уточнить`, как сервер отдаёт «профиль не заполнен».

## Сохранение паролей системой

- Статус: `нужно`. От способа входа не зависит.
- Чтобы iOS и Android предлагали сохранить и подставить ник и пароль, нужны:
  - iOS: в приложении entitlement убран (2026-11-04): личная команда Apple `KJMPGZ5P4U` не поддерживает Associated Domains, и сборка на устройство не подписывалась. Вернуть `webcredentials:druna.tg4.dev` в `ios/Runner/Runner.entitlements` (bundle ID `dev.tg4.druna`) — после перехода на платную команду; ID команды в AASA ниже тогда заменить. Серверу нужно отдавать `https://druna.tg4.dev/.well-known/apple-app-site-association` — сейчас 404:

    ```json
    { "webcredentials": { "apps": ["KJMPGZ5P4U.dev.tg4.druna"] } }
    ```

    `Content-Type: application/json`, без редиректов и без авторизации. Тот же файл понадобится для passkeys.
  - Android: `https://druna.tg4.dev/.well-known/assetlinks.json` с `package_name` `dev.tg4.druna` и `delegate_permission/common.get_login_creds`; SHA-256 сертификата подписи — `уточнить` (release-ключа пока нет).

## Восстановление пароля

- Статус: `уточнить`
- **Что нужно клиенту.** На шаге входа (`docs/design-system.md` §9.9) под полем пароля есть «забыл пароль?». Сейчас все источники отвечают «восстановление пароля пока не поддерживается» (`AuthFlowSource.resetPassword`).
- **Почему текущих вызовов недостаточно.** Сменить пароль без входа нельзя. Через почту — не будет (см. выше); канал — тот же Telegram, что для входа.
- **Правила для контракта** (в любом канале):
  - код или ссылка — одноразовые, живут до 15 минут, после 5 ошибок — 429;
  - ответ одинаковый, есть аккаунт или нет;
  - после смены пароля все прежние refresh-токены пользователя отзываются;
  - финальный вызов `{ …, password }` → новая пара токенов.

## Passkeys

- Статус: `уточнить`
- **Что нужно клиенту.** Вход без пароля: создать passkey для аккаунта и входить им; iOS предлагает его над клавиатурой в поле ника. UI — по дизайну автора, его пока нет.
- **Почему текущих вызовов недостаточно.** Сервер знает только пароли; WebAuthn-регистрации и проверки подписи нет.
- **Предлагаемый контракт** (WebAuthn, RP ID `druna.tg4.dev`):
  - `POST /auth/passkey/register/start` (с access token) → параметры создания с одноразовым challenge; `POST /auth/passkey/register/finish` — ответ устройства, сервер проверяет и хранит публичный ключ.
  - `POST /auth/passkey/sign-in/start` `{ username? }` → challenge; `POST /auth/passkey/sign-in/finish` — подпись → пара токенов.
  - Challenge создаёт и проверяет только сервер, один раз, с коротким сроком.
- Нужен тот же `apple-app-site-association` (`webcredentials`) и `assetlinks.json`, что выше.

## Приглашения на события

- Статус: `нужно`
- **Что нужно клиенту.** Режим друзей в календаре. Удержание дня или рисование в дне при выбранных в friend bar друзьях создаёт приглашение.
  - Организатор задаёт название, дату и время (или «весь день») и описание. После подтверждения друзья должны получить приглашение.
  - Форма события показывает, кто идёт, кого ждём и кто отказался. Приглашённый отвечает «Да» или «Нет», может передумать или снять ответ (снова «ждём»). «Возможно» убрано (2026-11-01). Организатор всегда идёт, его ответ не меняется; он правит время, название и описание или отменяет событие.
  - В профиле — список всех приглашений: ждут ответа, предстоящие, прошедшие.
  - Сейчас всё это работает только на демо-данных (`DemoInvitesSource`). С сервером клиент честно пишет «Приглашения пока не поддерживаются сервером».
- **Почему текущих вызовов недостаточно.**
  - Групповое событие (`/groups/:id/events`) не имеет участников и ответов. В группу добавляют сразу, без согласия, только друзей владельца, и удалить участника нельзя. Отказаться можно только выходом из группы.
  - Единственный сигнал «подтвердил» — `confirmedTime` участника группы. При добавлении он ставится в `now()`, поэтому «ещё не ответил» из него не вывести.
  - Создавать группу на каждое приглашение значит плодить группы, которые некому удалить.
- **Предлагаемый контракт** (`/api/v1/invites`, всё под Bearer):
  - `POST /invites` `{ title, description?, startTime, endTime, allDay?, invitees: [username] }` → `{ invite }`. Звать можно только принятых друзей, иначе 400 с перечнем.
  - `GET /invites?status=pending|upcoming|past&limit&offset` → `{ invites: [Invite], total }`. Приглашения, где я организатор или участник.
  - `GET /invites/:id` → `Invite`. Не участнику — 404.
  - `PATCH /invites/:id` `{ title?, description?, startTime?, endTime?, allDay? }` — только организатор. Ответы участников при смене времени: сбрасывать в `pending` или нет — `уточнить`.
  - `DELETE /invites/:id` — только организатор; у участников приглашение пропадает.
  - `POST /invites/:id/respond` `{ status: "going" | "not_going" | "pending" }` — только сам приглашённый, сколько угодно раз; `pending` снимает ответ. Организатору — 400.
  - `Invite`: `{ id, title, description, startTime, endTime, allDay, organizer: FriendInfo, participants: [{ user: FriendInfo, status: "pending"|"going"|"not_going", respondedAt }] , createdAt, updatedAt }`.
  - Добавить и убрать участников после отправки — `уточнить`. В клиенте пока нет.
- **Связь с другими данными** — `уточнить`:
  - Должно ли «иду» входить в свободное время и в занятость друзей? Клиент рисует принятые приглашения в календаре как свои события, поэтому логично — да.
  - Проверять ли пересечение с личными событиями? Сейчас личные и групповые события не проверяются друг с другом.
- **Push:** тип `invite_created` для приглашённых, `invite_answered` для организатора, `invite_changed` и `invite_cancelled` для участников (см. «Push и device token»).

## Push и device token

- Статус: `нужно`
- **Зачем клиенту:** о новых приглашениях, ответах на них и заявках в друзья пользователь узнаёт, только открыв приложение. Список в профиле обновляется при загрузке.
- **Что есть на сервере:** таблица `notification_outbox` (`user_id`, `type`, `payload`, `created_at`, `delivered_at`) с типами:
  - `friend_request` `{fromUsername}`;
  - `group_confirm` `{groupId}`;
  - `group_event_created` `{groupId, eventId, title, startTime}`.
  Отправки нет, и прочитать outbox нельзя: endpoint отсутствует.
- **Что отсутствует:**
  - регистрация device token: `POST /api/v1/devices` `{ token, platform: "ios"|"android" }`;
  - снятие токена при выходе: `DELETE /api/v1/devices/:token`;
  - доставка через APNs или FCM — `уточнить`, нужен ключ APNs и аккаунт Apple Developer;
  - чтение уведомлений внутри приложения: `GET /api/v1/notifications?since=` → `{ notifications: [{ id, type, payload, createdAt, readAt }] }` и `POST /api/v1/notifications/read` `{ ids }`;
  - типы для приглашений (см. «Приглашения на события»).
- На клиенте push-инфраструктуры нет: entitlements, `firebase_messaging` и запрос разрешения отсутствуют.

## Список событий: пагинация и диапазон

- Статус: `есть в API`, клиент не использует
- Зачем клиенту: календарь листается на месяцы вперёд и назад. Когда он перейдёт на сервер, ему нужны события видимого диапазона.
- Что не так: `GET /events/` по умолчанию отдаёт 50 событий. `DrunaRepository.listEvents()` не передаёт `limit`, `offset`, `dateFrom`, `dateTo` и не читает `total`, поэтому всё после 50-го теряется.
- Что сделать на клиенте: передавать `dateFrom`/`dateTo` видимых недель. Серверу — подтвердить, что фильтр по диапазону учитывает события, начавшиеся раньше `dateFrom`, — `уточнить`.

## Свободное время: часовой пояс и групповые события

- Статус: `уточнить`
- Что не так:
  - `POST /events/free-time` и `/groups/:id/free-time` берут день из строки `date` через `time.Parse("2006-01-02")`, то есть как сутки UTC. Клиент передаёт локальную дату, и у пользователя в UTC+3 окна сдвинуты на 3 часа.
  - Личное свободное время не учитывает групповые события пользователя (`group_id IS NULL`), хотя групповое учитывает личные события каждого участника.
  - Запрос только на один день.
- Предлагаемый контракт: принимать `timezone` (IANA) или `dateFrom`/`dateTo` в RFC 3339 с поясом. Учитывать групповые события и, когда появятся, принятые приглашения. Диапазон в несколько дней — `уточнить`.

## Группы: подтверждение времени и участники

- Статус: `нужно` (решение автора 2026-11-07: группы делаем полностью)
- Зачем клиенту: страницы групп справа от профиля, создание группы, группа
  в friend bar, которая выбирает занятость всех её участников.
- Что не так сейчас:
  - участника добавляют сразу, без его согласия (`POST /groups/:id/members`),
    а клиент после создания спрашивает «Отправить приглашение в группу?»;
  - убрать участника нельзя, переименовать группу нельзя;
  - в список групп (`/groups/list`) участники не входят — friend bar не
    может нарисовать группу без запроса на каждую;
  - у группы нет шрифта названия;
  - `confirmedTime` группы ставится при создании и больше не меняется;
    `GET /groups/:id` отдаёт `confirmedTime` каждого участника, а модель
    клиента `GroupSummary` его теряет.
- Предлагаемый контракт (автор: «хранить список участников, название группы,
  шрифт; цвета клиент читает у профилей»):

  - push `group_invite`.

  — нужна страница и universal link, как у профиля (`уточнить`).

  состав участников совпадает с группой. Если нужны события именно «в

## Календари Apple, Google и Outlook

- Статус: `нужно`
- Зачем клиенту: с 2026-11-03 клиент читает календарь устройства (Apple Календарь на iOS, календарь устройства на Android) и показывает его события среди своих, а свои пишет в календарь «Druna» на устройстве. Всё это — на устройстве, без сервера. Сервер о внешних событиях не знает, поэтому они не попадают ни в `free-time`, ни в занятость, которую видят друзья.
- Продуктовое решение (автор, 2026-11-03): источник занятости — календари, которые пользователь включил в меню календаря. **Названия друзьям не передаются**, только интервалы; позже — ярлыки («работа»). Событие с пометкой «свободен» занятостью не считается.
- Что отсутствует: приём интервалов занятости с клиента и их учёт в `free-time` и в занятости друзей.
- Предлагаемый контракт:
  - `PUT /users/me/external-busy` — заменить всю внешнюю занятость пользователя: `{ "from": "…", "to": "…", "intervals": [{ "start": "…", "end": "…", "allDay": false }] }`. Окно — от месяца назад до года вперёд; интервалы вне окна сервер удаляет. Без названий, описаний и идентификаторов событий.
  - Учитывать эти интервалы в `free-time` и в занятости, которую видят друзья, наравне с событиями Druna.
  - Ярлыки (`label: "работа"`) — `уточнить`, когда автор их опишет.
  - Google и Outlook через OAuth на сервере — `уточнить`: на устройстве их календари и так видны, если подключены к системному календарю.

## Профиль: имя и аватар

- Статус: `нужно`
- **Что есть:** `PATCH /users/me` принимает `name` и `avatarURL`. С 2026-10-30 профиль в новом UI правит имя.
- **Что не так:**
  - SQL обновляет поля через `COALESCE(NULLIF($x,''), …)`: пустая строка значит «не менять». Поэтому имя нельзя стереть (клиент и не даёт), а аватар нельзя убрать.
  - Загрузки файла нет: только URL уже размещённой картинки. Выбора фото с устройства в новом UI нет, люди везде показываются цветом и буквой.
  - `username` и `email` не меняются.
- **Предлагаемый контракт:**
  - upload аватара (multipart или presigned URL) с возвратом постоянного URL — `уточнить` вместе с лимитом размера;
  - `avatarURL: null` убирает аватар.

## Событие на весь день

- Статус: `нужно`
- Зачем клиенту: в листе события нового календаря есть переключатель «Весь день». Событие на весь день рисуется полосой без времени, в том числе на несколько дней подряд. Пока календарь работает на демо-данных, флаг живёт только в памяти. Приглашение тоже может быть на весь день.
- Что отсутствует: в DTO события есть только `title`, `startTime`, `endTime`, `type`. Сервер не отличает «весь день» от события 00:00–00:00, а `endTime` должен быть строго позже `startTime`.
- Почему текущих вызовов недостаточно: если хранить «весь день» как 00:00 → 00:00 следующего дня, то настоящая встреча с полуночи до полуночи станет неотличима от события на весь день. Кроме того, у UTC-времени полночь в одном поясе — это середина дня в другом.
- Предлагаемый контракт: поле `allDay: bool` в create/update/list для личных и групповых событий и в `Invite`. Для `allDay = true` даты передаются без времени (`startDate`, `endDate`, конец включительно) или как полночь в поясе владельца — нужно `уточнить`. Уточнить также, как такие события учитывает `free-time`.

## Повторяющиеся события

- Статус: `нужно`
- Зачем клиенту: в листе события есть «Повтор»: каждый день, каждую неделю (с выбором дней Пн–Вс), каждые 2 недели, каждый месяц, каждый год, «Дополнительно» (каждые N дней, недель, месяцев или лет) и окончание повтора (никогда или дата). Сейчас серия разворачивается на клиенте и не сохраняется.
- Что отсутствует: поле правила повтора в событии, развёртывание повторов в `GET …/events` по `dateFrom`/`dateTo`, учёт повторов в `free-time` и в проверке пересечений, правка и удаление одного повтора или всей серии.
- Почему текущих вызовов недостаточно: создать копии события на N недель вперёд можно, но тогда серия не связана: «изменить все» и «удалить все» невозможны, бесконечный повтор не выразить, а сервер отклонит копии, которые пересекаются с другими событиями.
- Предлагаемый контракт: поле `repeat` по мотивам RRULE (RFC 5545): `{ "freq": "daily|weekly|monthly|yearly", "interval": 1, "byWeekday": [1, 3], "until": "YYYY-MM-DD" | null }`. В списке событий — развёрнутые повторы с `seriesID` и датой повтора. Правка одного повтора — `уточнить` (исключения EXDATE или отдельное событие-исключение). У приглашений повтора нет.

## Занятость друзей

- Статус: `нужно`
- Зачем клиенту: в календаре друзей (friend bar) выбранные друзья показываются полосами занятости их цвета. Без сервера клиент рисует только демо-расписания (переключатель в настройках), а в обычном режиме честно пишет «Расписание друзей пока недоступно».
- Что отсутствует: способ получить занятость друга. `GET /api/v1/events` отдаёт только свои события, `POST /groups/:id/free-time` — только общие свободные окна группы, и то по одному дню.
- Почему текущих вызовов недостаточно: окна группы не говорят, кто именно занят и когда, требуют создать группу и не покрывают месяц.
- Предлагаемый контракт: `GET /api/v1/friends/:username/busy?dateFrom=YYYY-MM-DD&dateTo=YYYY-MM-DD` → `{ "busy": [{ "startTime", "endTime", "allDay" }] }` — интервалы без названий и типов, повторы уже развёрнуты, принятые приглашения включены. Только для принятых друзей. Нужна ли отдельная настройка приватности («скрывать занятость») — `уточнить`. Вариант для нескольких друзей одним запросом — `уточнить`.
- Календари устройства (решение автора 2026-11-04): события из календарей, которые пользователь сам выбрал для импорта (дни рождения тоже), считаются занятостью как все и должны быть видны друзьям. Сервер о них не знает — нужен способ передать занятость с устройства, например `PUT /api/v1/me/external-busy` с интервалами без названий — `уточнить`.
